# How Detent's code is organised

A map for finding your way. The rules for each layer are in [AGENTS.md](../AGENTS.md), and the full design is in the [PRD](../detent-prd-v3.md).

## The idea in one paragraph

Detent turns a project's planning documents into tickets, then runs one fresh Claude Code session per step of each ticket: implement, review, and when a check fails, diagnose and research. Every move a session wants to make goes through the **referee**, which checks it against the state machine, the ticket's write surface and the budgets before it is admitted and journaled. `detent init` builds the plan; `detent run` works through it.

## Folders of `src/`

| Folder | What it does | Start with |
|---|---|---|
| `cli/` | The `detent` command: `init` and `run`, and the plumbing commands (`status`, `report`, `doctor`, `approve`…) | `index.ts` |
| `init/` | Everything `detent init` does, phase by phase: auditing the documents, writing and validating the pack, slicing, planning, presenting | `pipeline.ts` |
| `kernel/` | The heart: the state machine, tickets and their state, budgets, the journal, and the loop that drives a run | `machine.ts`, `driver.ts` |
| `referee/` | The referee as an MCP server: the plugin's sessions call it, and it uses the same entry point as the headless driver | `server.ts` |
| `sessions/` | Starting and talking to Claude Code sessions: the Agent SDK backend, prompts, the containment guard, prices | `backend.ts`, `sdk.ts` |
| `adapter/` | The project's own commands: discovering, binding and running its test, lint and build gates, and noticing when they change | `run.ts`, `bind.ts` |
| `plugin/` | The containment hook in plugin form, bundled into `hooks/dist/` by `npm run plugin` | `hook.ts` |
| `fs/` | The `.detent/` folder: what is committed and what stays local | `layout.ts` |
| `schemas/` | The shapes of every record, checked with zod. Every other layer may use them | `common.ts`, `states.ts` |
| `eval/` | Measuring whether a cheaper model or effort level keeps quality, on fixed sets | `run.ts`, and [evaluation.md](evaluation.md) |

## The rule between layers

`kernel/` decides; the other layers report. Lint enforces it:

- `kernel/` may use `sessions/` only through the `SessionBackend` interface in `sessions/backend.ts`, and never the SDK directly.
- Only `kernel/` changes ticket state (`kernel/tickets/mutations.ts`) or applies events to the state machine. Other layers read ticket state through `kernel/tickets/readers.ts`.
- `schemas/` sits below everything and may be imported anywhere.

## Outside `src/`

| Path | What it holds |
|---|---|
| `tests/` | The tests, in folders that mirror `src/`, plus `arch/` (the layer rules), `docs/` (tests that check the README and the PRD), `sec/` (containment and security cases), `perf/` and `oracle/` (the tests ported from the Python reference) |
| `prompts/` | The prompt of each role. Their hashes are pinned in `manifest.json`: run `npm run prompts` after changing one |
| `agents/`, `skills/`, `hooks/` | The plugin's files. `agents/` and `hooks/dist/` are generated by `npm run plugin` |
| `scripts/` | The repository's own tools: the checks, plugin build, evaluation runs |
| `archive/` | Review records from before October 2026, which older comments cite by id |
